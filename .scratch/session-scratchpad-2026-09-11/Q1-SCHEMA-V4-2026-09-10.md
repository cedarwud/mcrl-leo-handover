## 3. The derivability gate

### What authenticated state contains [run]

Per anchor, the datepool physics shard carries three record kinds:
`anchor_context` (the base `default_mapping` of all 100 users),
`row_physics` (boundary-0 geometry of every candidate **and** of the user's
base identity, including `nominal_gain_hex` and the live flags), and
`configuration_physics` (the evaluated whole-configuration outcome). The last
kind is the output of the label computation itself (`required_power_w_max`,
`rf_cap_hits`, per-user bits) and is **excluded as a feature source** — using it
would feed label physics into the input.

### Physics the fields are built from (all in `mcrl-v025-retrain-ws/src/mcrl/physics_v025`, hashes pinned in the build)

- `gamma(n) = rate_target_sinr(RATE_TARGET_BPS, BEAM_BANDWIDTH_HZ, n)`, which
  applies `required_se = rate_target_bps * occupancy / full_bandwidth_hz`
  ([acm.py:95](/home/sat/mcrl-v025-retrain-ws/src/mcrl/physics_v025/acm.py:95));
  the label path builds exactly this table at
  [batch.py:106-113](/home/sat/mcrl-v025-retrain-ws/src/mcrl/physics_v025/batch.py:106).
  `RATE_TARGET_BPS = 50e6` (constants_v025.py:47), `BEAM_BANDWIDTH_HZ = 500/3 MHz`
  (constants_v025.py:25).
- noise `N = noise_power_w(BEAM_BANDWIDTH_HZ)` (channel.py:41-46; batch.py:115).
- occupancy counts **live** users on a beam (batch.py:205-209).
- the a-r0 power solver starts at zero (batch.py:254) and iterates
  `min(cap, gamma(n) * (N + I) / g_nominal)` (batch.py:261-264), forcing the cap
  when `gamma` is `None` (batch.py:252, 266); `g_nominal` is
  `arrays.nominal_gain` (batch.py:217), the same array the physics shard
  serialises (`build.py:292`). **Its first iterate therefore has `I = 0`:
  `p1 = min(cap, gamma(n) * N / g)` is the solver's own first step, not a new
  model.** Iterates are rejected if they decrease (batch.py:267-269), so `p1` is
  a lower bound on the converged power, and a user bound at `p1` stays bound
  [derived].
- cap binding is `p >= cap − 1e-9` (batch.py:390-391); `BEAM_RF_CAP_W = 1.65`
  (constants_v025.py:34).
- the physics' own RF aggregate over transmitters is a max (batch.py:351-352).

Where the brief says the cap "binds at occupancy 12 on a representative
isolated link": at the **median legal-option gain (−107.835 dB)** the first
iterate is **0.9379 of the cap at occupancy 12** and the rate target is
**ACM-infeasible (forced cap) from occupancy 13**; at the 10th-percentile gain
(−110.21 dB) it binds at 11 [run]. Occupancy 12 is the last ACM-feasible value
(`required_se` 3.6 ≤ top SE 3.711) [derived]. Observed post-join occupancy never
exceeds 7 on these anchors [run].

### Incumbent set, and its authentication [run]

For option (focal user *u*, beam *b*): incumbents = live users ≠ *u* that the
anchor's base `default_mapping` places on *b* — the same focal-absent
counterfactual as v2's `background_occupancy_excluding_focal`, which the pilot
computes from the same base mapping
([run_v025_pilot_c3.py:230](/home/sat/mcrl-v025-retrain-ws/scripts/run_v025_pilot_c3.py:230), `:648`).
Each incumbent's gain is its row-physics `default_geometry_offsets_0_1_2_3[0].nominal_gain_hex`,
the boundary-0 geometry of its base identity (`build.py:571-582`). Checks, all fail closed:

- the recomputed live incumbent count equals v2 slot 3 × 10 on **all 81,638 legal rows** (0 mismatches);
- every user's default geometry identity equals `default_mapping`, and is identical across that user's rows;
- every focal and incumbent nominal gain matches the provider formula recomputed from angle, slant and elevation with **maximum relative residual 0.0**;
- 0 base-mapped users are non-live; 0 legal focal options are non-live; `cell_rekeyed_users` is empty at all 93 anchors.

## 4. Per-arm maskability — how a consumer selects a subset

One stored vector per row (the 19-wide `both` vector: v2 order, then gain, then
the three congestion fields). A subset is a **column projection**; the family
file `artifacts/q1v4-schema-family.json` lists all 16 subsets of the 4 added
fields with their index lists, schema digests, Q1/member/C3 widths. `none` is
byte-identical to the Q1 v2 schema object and `gain_only` to the Q1 v3 schema
object — the build asserts both, and asserts on every row that the `none`
projection equals the authoritative v2 module's projection and the
`gain_only` projection equals the v3 module's vector [run].

To select a subset:

1. Choose `none | gain_only | congestion_only | both`; its view is
   `artifacts/q1v4-<subset>-exact-label-corpus-93-20260911/`.
2. In the training process, call `q1v4_reader.register_subset_adapter(runner, subset)`
   **before** `runner.load_corpus(...)` or `runner.run(...)`. It registers a
   digest-keyed, in-process encoder adapter; no production source is edited.
   The reader resolves the encoder from each row's own `q1_schema_sha256`, so a
   corpus/subset mismatch fails closed.
3. `q1v4_reader.dry_run` shows the fail-closed checks: corpus digest vs build
   receipt, Q1 digest, Q1/Q2/member/C3 widths vs the family table, 93 anchors,
   and the five-arm inventory.
4. Any other subset (for example, dropping one flagged field):
   `project_subset_view.py <new-dir> <fields…>` projects the `both` view in
   about a minute with no physics. **Self-test [run]:** regenerating
   `congestion_only` from `both` reproduced all 90,938 source rows identically
   except the lineage digest, all 93 headers, and all 93 coalition shards
   byte-for-byte.

Launch note [run, static read of learner.py]: `V1LineageOrchestrator`
checkpoints bind the corpus through batch digests that hash each row's
`q1_schema_sha256`; they carry no separate encoder digest, so an
adapter-wrapped launch cannot mislabel its checkpoints. The adapter must be
registered in **every** process that reads these rows or their checkpoints.
The full `runner.run` path (synthetic fixture gate, checkpoint write/restore)
was **not** exercised here because it trains.

**The gain finding, stated plainly [run].** For all 7,238 complete-table users
at all 93 anchors, the descending-gain ordering of the 9 legal slots is **one
single permutation**: slot 0 is the reference action and is **always the
lowest-gain legal option**, and slots 1–8 are in descending nominal gain
(rank-transformed cross-user agreement **1.0000**). The mechanism is inferred:
a top-8-by-gain candidate catalogue plus the reference, where a 10-slot table
arises exactly when the reference falls outside the top 8. So by construction,
the gain field's within-user ordering is identical for every user, and only its
magnitudes vary (within-user spread median 8.9 dB, p10 3.7, p90 21.9). About
0.106 of the 10-slot value comes from the null slot's `0` convention inherited
from v3, which sits at least 1.02 above every legal value (legal range −1.84 to −1.02; median gap 1.08). **This is not a reason the
field is uninformative** — its motivation (the 41.62 Mbit/J rule is
inexpressible without per-option gain) is about magnitude and a
within-user choice. **It is a direct risk that any head leaning on it produces
the same Q-row shape for every user**, i.e. that C1 collinearity rises further
above v2's (Q-ROW measured v1→v2 +0.2143 on C1) [inferred]. Before a gain arm is
trained, record the prediction: gain arms raise C1 Q-row collinearity relative
to `none`/`congestion_only`. Then measure it with the Q-ROW instrument on
their checkpoints.
