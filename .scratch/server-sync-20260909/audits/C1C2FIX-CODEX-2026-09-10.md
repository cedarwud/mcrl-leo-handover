## A. The C2 survival defect

### Finding

`state.py` does not compute survival, and the serializer is not overwriting or defaulting the flag. `extract_source_rows` appends `float(forecast.valid)` and `float(forecast.survival)` verbatim (`src/mcrl/stagec_v025/state.py:426-433`). The defect is upstream in the legacy pilot's primitive encoder adapter:

- `_build_anchor_rows_primitive` defines survival as `future_metric["legal"] and identity is not None`, then writes that same value to both `valid` and `survival` (`scripts/run_v025_pilot_c3.py:416-430`). `_primitive_metrics` defines `legal` only from future visibility, D2 eligibility, and cell reachability (`scripts/run_v025_pilot_c3.py:323-352`). It never asks whether the coupled evaluator serves the user.
- The exact projection uses a different predicate. `_batched_stage2_forecasts` evaluates the whole configuration, forms `changed = {u: candidate_mapping[u] != future_transition[u]}`, and requires **every changed user** to be in `profile.score.served_phy` (`.scratch/multi-catfish-v025-physics-successor/probe/run_v025_matrix_probe.py:1612-1638`).
- The non-fallback source builder would pass those exact `row.valid` and `row.survives` values into `ForecastObservation` correctly (`scripts/run_v025_pilot_c3.py:665-672`). Therefore this is specifically an adapter-path semantic misencoding, not a mutation in `state.py`.

For the real witness, both anchors have the same physical step-0 tape, current base mapping, incumbent mapping, and focal candidate `(user=6, action=(65028,44))`. Nevertheless, the future carrier transition makes the target predicate range over 93 changed users at each offset for anchor 0, but only the focal user for anchor 1. Thus the target uses the same predicate on different `changed` inputs across anchors, while the primitive encoder uses an entirely different predicate.

| Anchor | Stored Q2 `survival[1:3]` | Exact projection `survives[1:3]` | Exact C2 |
|---:|---:|---:|---:|
| 0, `nearest-eligible` | `(1,1,1)` | `(0,0,0)` | `60102789335062397912351470235270 / 11110569965387252983357173269901` = `5.4095145003632172...` |
| 1, `stay-if-possible` | `(1,1,1)` | `(1,1,1)` | `2149528301326970807719944431070731 / 111105699653872529833571732699010` = `19.346696956352321...` |

The absorbing rule is applied to the target but not to the encoded row. `c2_persistence_forecast` maintains `alive`; a first invalid/non-surviving projection makes every later offset a loss (`src/mcrl/physics_v025/targets.py:289-310`). Q2 stores three independent supplied booleans and has no cumulative `alive` transform. In this witness the distinction begins at offset 1, so anchor 0 incurs all three losses.

Classification: **BOTH**.

1. **ENCODER_BUG:** the primitive adapter labels geometric legality as both validity and coupled survival, although Q2 advertises distinct `valid` and `survival` fields. This is the immediate reason the stored row misreports all three flags.
2. **SUFFICIENCY_GAP:** the exact target flag is genuinely unavailable under the governing admissibility rule. It depends on a future carrier transition and a candidate whole-configuration coupled served set. The two witness inputs are identical at decision time, so no admissible deterministic feature can distinguish their target values. This also exposes a target-context defect: unrelated changed users can decide a focal action's “survival.”

Across the two cheap anchors, 822 of 1,784 valid nonreference rows have at least one stored-vs-exact **survival** mismatch (792/892 at anchor 0 and 30/892 at anchor 1), totalling 2,406 offset flags. Additionally, 200 rows have validity mismatches (600 offset flags). Counting a row affected by either boolean gives 1,022/1,784 rows. These anchors contain the previously established 62 exact C2 collision groups.

The admissible C1 repair buys **no measured predictive power**. Its value is exactly `1.0` at all 30 corpus anchors because every current base configuration reaches the RF cap, so standardization removes it. This negative result is not evidence that the feature is wrongly chosen for identifiability; it shows that breaking one contract witness does not supply variation useful on this corpus. C2 is unchanged because no admissible separator exists.

The leaky rows are only algebra checks. C1 OLS receives candidate/default whole-network bits, energy, and Phi; C2 OLS receives per-offset candidate/default outcome terms plus expanded absorbing state. Their `EV=1` merely recovers the target definitions and says nothing about deployable prediction.

## D. Consequences

### Expected pooled-energy-efficiency effect (under 200 words)

C1 cannot presently be expected to raise pooled energy efficiency. Its Q-only held-out EV is worse than the mean predictor, and the smallest admissible collision-breaking feature is constant on this sample and changes nothing. The exact C1 label is structurally sensitive to coupled whole-network effects that the action-local row still does not represent. A training run would not repair missing information and is not authorized by this diagnostic.

C2 also cannot presently be expected to raise pooled energy efficiency. Although Q2's held-out EV is positive (`0.2107`), its stored survival semantics are wrong on 822/1,784 two-anchor rows, and the exact target varies with future carrier-transition context absent from admissible deployment inputs. Correcting offline flags by copying coupled forecast outcomes would be leakage, not a deployable encoder repair. Before any efficacy claim, the focal-survival target must be made a function of admissible decision-time information (or the per-user C2 head design reconsidered), then evaluated on a fresh untouched split. No pooled-EE conclusion follows here.

### Minimum pipeline change and sealed-lineage stop (under 200 words)

For C1 only, `src/mcrl/stagec_v025/state.py` would need a v2 Q1 `FeatureSpec`, an `ActionEvaluation` field, and extraction of the 17th scalar. `scripts/run_v025_pilot_c3.py` would populate it from the cached decision-time `base_profile.required_power_w_max / BEAM_RF_CAP_W` in both source-builder paths. `tests/stagec_v025/test_stagec_pipeline.py` and relevant state/shard tests would need the new ordered width/schema assertions; synthetic rows already derive width from `Q1_FEATURES` but fixtures must be checked. `scripts/diagnose_v025_c1c2_sufficiency.py` contains the diagnostic-only measurement implemented here.

This changes `Q1_SCHEMA_SHA256`. Existing sealed JSONL shard headers, merged manifests, trained checkpoints, and frozen artifact digests would no longer match and must **not** be edited in place; adoption requires a newly versioned, newly generated artifact/manifest/checkpoint lineage. C2 additionally requires a target-contract decision, not an encoder-width change. Per the stop rule, no production schema, sealed artifact, frozen manifest, or training pipeline was modified.
