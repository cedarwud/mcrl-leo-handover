## Scope

This is the **H4 probe**: for the CF3PILOT ratio learner (A1 OFF / A2 CF3 / A3 NULL3), does the
energy head (`Q̃_E`, weighted by η in the deployed rule `Q̃_B − η̃ Q̃_E`) ever actually change which
action gets taken, and where does a simple, explicit "own-bits" rule (SINR and load only, no
learning) sit relative to the non-learned reference rules and the learners. No training occurred;
every number below comes from rolling out already-frozen final checkpoints or hand-written rules on
already-declared episode sets.

## 1. Argmax-flip fractions (deployed trajectory; evaluation episodes)

Method: roll out the **deployed** rule (η = the checkpoint's own η, λ = 0 — asserted per checkpoint,
not assumed) on the 24 evaluation episodes; at every decision (non-empty mask) **also** compute, with
the *same* `CFRatioTrainer.greedy_actions` call (only `tr.eta`/`lam` varied — never a different
tie-break implementation, so a "flip" can never be an implementation artifact):

- **(i)** the counterfactual score at η→0, λ=0 (`Q̃_B` alone), vs the deployed action;
- **(iv)** the counterfactual score at η=deployed, λ=1 in the heads' units (`Q̃_B − η̃ Q̃_E − Q̃_H`),

## 3. An explicit own-bits greedy rule

Score for each legal candidate beam `a`: **`(1 / (load_a + 1)) · log2(1 + gamma_a)`**, implemented the
same way `cf_sources.py`'s rules are (reads only raw `UserState` fields, touches no trained network),
masked argmax, first index on ties:

- `gamma_a` = `UserState.channel_quality[a]` — the **raw** nominal SINR/gain. `state_encoding.py`'s
  `encode_state` applies `log1p` to this field only when building the NN's 112-dim block-2 input;
  this rule bypasses that and reads the raw field directly, exactly like `cf_sources.make_rule`'s
  `gain = np.asarray(s.channel_quality, ...)`.
- `load_a` = `UserState.beam_loads[a]` — the **raw previous-step user count** on beam `a`.
  `state_encoding.py` divides this by `num_users` (=100) only when building the NN's block-4 input;
  this rule does **not** divide, exactly like `cf_sources.r_no_new_beam`'s
  `load = np.asarray(s.beam_loads, ...)`, and matching the task's own wording "previous-step user
  count."
- Negative `gamma_a` is floored at 0 before `log2(1+·)`, mirroring `state_encoding.py`'s own
  `np.maximum(snr, 0.0)` precedent. **In practice this never activated**: on EACH episode set
  independently (672,000 `channel_quality` observations per set: 100 users × 28 candidates × 10
  steps × 24 episodes, counted only over users with a non-empty mask that step), `n_gain_negative = 0`
  and `min_gain = 0.0` exactly — the floor is documented but inert on this data. Observed ranges:
  `gamma` ∈ [0.0, 1099.55] (calibration) / [0.0, 959.84] (evaluation); `load` ∈ [0.0, 13.0]
  (calibration) / [0.0, 12.0] (evaluation).

Per-served-user rate mean is **not** back-derived from `system_throughput_bps` (that would silently
assume it decomposes exactly into `Σ r1_throughput` over served users — an assumption this probe
does not make). It is measured directly: `RewardComponents.r1_throughput` (bit/s, the same field
`cf_ratio.cf_reward_matrix` reads for its `B_u` head), accumulated over served user-steps only, via a
rollout-loop extension (`pooled_rollout_with_user_rate`) whose *shared* fields (ee/bits/joules/
h_inter/h_intra/served/beams) are cross-checked bit-for-bit against `calibration.json` (produced by
the unmodified `cf_ratio.pooled_rollout`) for the two reference rules on calibration episodes — see
§5.

**Reading:** own-bits, despite explicitly modelling load-balancing (the `1/(load+1)` term that neither

on both episode sets, and also has the *highest* `H_inter` and lowest lit-beam count of the three —
i.e. it is not simply "the same ranking with a tie-breaker," it produces a visibly different (and, on
this metric, worse) policy. This is reported as a plain descriptive fact, not spun as favourable to
either the rule-based or learned family.
