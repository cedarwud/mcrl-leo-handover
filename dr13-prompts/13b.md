## Bottom line

**Your first priority should be to reduce the work needed to certify the original selection, while putting an independent deadline controller around the computation.** Simply switching to “return the best candidate found so far” solves a different problem: it can prevent an empty return, but it does **not** preserve the candidate that the original procedure would have selected.

Three properties need to be kept separate:

| Property                         | What it guarantees                                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Deadline-safe return**         | A valid assignment is available before 10 seconds, even when the optimiser is unfinished.                        |
| **Monotone anytime improvement** | On the same frozen input, the best completed candidate never gets worse as computation continues.                |
| **Selection preservation**       | The returned candidate is exactly the one the reference procedure would select, including its tie-breaking rule. |

The first two do not imply the third. Under your restriction, an unfinished search can return a new assignment **only when it has already established that the remaining work cannot change the winner**. Otherwise, retaining the previous assignment remains necessary.

I interpret “lossless” below as preserving the **completed reference procedure’s selection**, not preserving its existing timeout-to-default behaviour. Preserving the latter literally would prohibit fixing the fallbacks you are trying to remove.

## 1. Anytime selection: separate computation from commitment

The relevant distinction in the anytime-algorithm literature is between an **interruptible algorithm**, which has a usable result when interrupted, and a **contract algorithm**, which needs its allocated computation to finish before its result is usable. A sequence of expensive physics solves is not automatically interruptible merely because the outer search checks a clock. 

### The engineering architecture I would use

Use a small supervisor that owns the authoritative result, and separate workers that own all unfinished computation.

**Freeze the decision input.** At the beginning of an epoch, create an immutable snapshot containing the anchor, physical state, constraints, model configuration and any random-number state relevant to evaluation. Give it an epoch identifier. Start an absolute, monotonic-clock deadline at the actual beginning of the budget—not after preprocessing.

**Install the fallback immediately.** The supervisor already holds the previous assignment, assuming it remains valid under your specified fallback policy. That provides availability without waiting for any new physics solve. However, yesterday’s or the previous epoch’s objective value cannot establish improvement under the new snapshot. A monotonicity claim needs scores evaluated or bounded for the same current input.

**Keep two distinct records:**

* `best_completed`: the best fully evaluated, feasible candidate received so far.
* `reference_certified`: a candidate whose equivalence to the reference procedure’s final selection has been established.

Under ordinary anytime operation, `best_completed` can be emitted. Under your strict lossless policy, only `reference_certified` is eligible to replace the fallback.

**Publish complete objects, never partially edited assignments.** A worker produces a complete assignment, score or certified bounds, feasibility status, tie-breaking key and epoch identifier. The supervisor validates the message and replaces its retained result in one bounded commitment operation. Workers never mutate that retained object.

**Close acceptance before the external deadline.** At an internal cutoff, the supervisor freezes the result and performs only bounded output work. It does not start another physics solve, wait for a worker, drain an arbitrary queue, flush a large log or serialize an unbounded object.

Conceptually:

```text
At epoch release:
    retain valid previous assignment
    freeze input snapshot
    set absolute acceptance cutoff and external deadline
    launch computation on the frozen snapshot

Before acceptance cutoff:
    accept only complete, current-epoch result messages
    update best_completed using the reference comparison rule
    update reference_certified only when its certificate is valid

At acceptance cutoff:
    freeze reference_certified, or retain previous assignment
    publish the already validated assignment through a bounded path
    reject all late results for this epoch
```

This is an architectural sketch, not a claim that a normal Python event loop provides hard real-time execution.

### Do not make returning depend on stopping the solver

A solver’s own time limit is useful as a cooperative request, but not as the outer guarantee. Gurobi explicitly documents that termination checks can occur after a specified limit has been exceeded. ([Gurobi 文檔][1])

There are also important implementation traps. Python futures cannot cancel work that is already running, and leaving an executor context normally waits for its work to finish. Python’s multiprocessing documentation warns that forcibly terminating a process while it uses a queue or pipe can corrupt that channel, and terminating one while it holds a lock can cause deadlock. ([Python documentation][2])

My design consequence is: **the return path must not need any resource held by the worker being interrupted.** Retain the last complete result in supervisor-owned memory; reject incomplete messages; do not join the worker before returning. Cleanup must also be bounded or isolated so that unfinished workers cannot accumulate and interfere with the next 30-second cycle.

A genuinely hard return guarantee additionally requires a bound on scheduling delay and the publication path. Linux’s deadline scheduler, for example, provides CPU reservations with admission control and schedulability conditions; it is not a blanket guarantee for arbitrary blocking, I/O and shared-resource behaviour. ([Linux Kernel 文檔][3])

### How partial evaluation should be scheduled

For your expensive oracle, I would distinguish three stages:

**Cheap checks and bounds first.** Apply necessary feasibility conditions, exact cache lookups and any certified upper bounds before launching a full solve.

**Refine candidates that could still win.** A suspended solve may retain its iterate, residual and valid objective enclosure. A partial iterate is not an evaluated candidate. It becomes useful for pruning only when it establishes that the candidate cannot beat the incumbent.

**Finish enough work to certify the winner.** Finding a strong candidate early and proving that it wins are different milestones. Under your rule, the latter is the operative deadline.

For a fixed candidate pool, changing evaluation order can improve the time to a useful incumbent and sometimes the time to certification. But under an interruption it can change the best-so-far result. With an adaptive generator, it can also change which candidates are generated next. Consequently, evaluation reordering is lossless only with the appropriate completion or equivalence argument.

Monotonicity here means nondecreasing incumbent value **within one frozen epoch**, with plateaus between completed evaluations. It does not promise an improvement every second, an improvement across changing network states, or a non-default answer before the deadline.

## 2. Where the budget goes: measure oracle work and search work separately

Your coupled fixed-point solve makes evaluation the leading suspect, but the supplied latency range does not establish where time is spent.

Also, “evaluation versus search” is not a clean dichotomy. Search determines the number and difficulty of evaluations. An implementation can spend almost all its time inside the oracle because the search repeatedly asks redundant or unpromising questions.

### The profiling breakdown that would answer this

For sequential execution, use an exclusive wall-time ledger:

$$
T =
T_{\text{input/precompute}}
+T_{\text{generation}}
+T_{\text{search bookkeeping}}
+\sum_{j=1}^{N_{\text{unique solves}}}T_{\text{oracle},j}
+T_{\text{validation/output}}
+T_{\text{other waits}}.
$$

Do not count an oracle call both inside cumulative search time and again as evaluation time. For parallel execution, analyse the critical path rather than adding overlapping wall times.

For each epoch, I would record the number of proposed candidates, unique assignments, cache hits, exact solves, safely pruned candidates and fixed-point iterations. Split each oracle call into setup, iteration/linear-algebra work and final scoring. Record CPU time alongside wall time to help distinguish computation from waiting.

Most importantly, record three timestamps:

**Time to first usable new candidate; time when the eventual winner was first found; time when the reference winner was certified.**

For example, finding the eventual winner at 2 seconds but certifying it at 9.9 seconds calls for better bounds or cheaper elimination of competitors—not necessarily better candidate generation.

Use profiling to locate costs, then benchmark the deadline distribution separately. Python’s documentation explicitly distinguishes profiling from benchmarking because instrumentation introduces overhead and can distort comparisons. ([Python documentation][4])

### The first speedups I would investigate

**Exact deduplication and memoisation.** Different coalition descriptions can produce the same full assignment. Evaluate that assignment once when the oracle is deterministic and the complete dependency state is identical.

**Per-epoch invariant caching.** Hoist computations that truly do not depend on the candidate. Depending on your equations, examples might include geometry, action-independent channel coefficients or fixed constraint data. Do not treat interference, solved powers or other coupled outputs as invariant merely because only a few agents moved.

**Remove repeated setup and copying.** Inspect whether every candidate reconstructs the same model, allocates large matrices, copies the entire network state or recomputes scores during sorting. These are good audit targets because changing the implementation may leave the mathematical search untouched.

**Warm starts and parallelism—but with additional checks.** Warm-starting a fixed point is not automatically lossless: changing the initial point could select another solution when the fixed point is nonunique, or change a finite-tolerance score. Parallel evaluation must preserve the reference’s comparison and tie rules, and must not let completion order alter adaptive search decisions.

The general reproducibility issue is real even in established solvers: Gurobi documents that wall-clock termination can produce different outputs on identical inputs, and provides a deterministic work-based stopping criterion for a different reproducibility contract. Such a work limit does not itself guarantee wall-clock completion. ([Gurobi 文檔][5])

### Surrogate shortlisting: useful generally, inadmissible here without a bound

Surrogate-guided reduction of expensive simulation evaluations is an established pattern. Sandia’s Dakota, for example, documents a method that optimises a surrogate and evaluates selected points using the underlying “truth” model. ([Dakota Documentation][6])

But your constraint rules out an ordinary learned top-\(k\) shortlist:

> Exact evaluation of the shortlisted candidates does not establish that an excluded candidate would not have won.

A surrogate is compatible with strict losslessness when it is used for ordering only, with eventual complete or certified coverage, or when it has a **valid error envelope** that yields a safe bound. Test-set accuracy, correlation and an empirical confidence interval are not deterministic bounds on every candidate the search may encounter.

## 3. Lossless pruning: what can actually be certified?

First freeze the object being preserved:

$$
a_{\mathrm{ref}}(s)
=
\text{output of the completed reference procedure on snapshot }s.
$$

That definition needs the candidate-generation rules, constraints, numerical oracle, stopping tolerances, random choices and tie-breaking rule. Preserving its output is not necessarily the same as finding the global optimum over all coalition/destination combinations.

### Techniques and their proof obligations

| Technique                            | What must be established for selection preservation                                                                                  |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Memoisation and deduplication**    | Reused evaluations have identical relevant inputs and semantics. Skipping them does not alter random state or adaptive control flow. |
| **Invariant hoisting / exact reuse** | The cached quantity is independent of all changed variables, including indirect fixed-point feedback.                                |
| **Cheap infeasibility rejection**    | The rejected candidate necessarily violates a constraint under the reference’s feasibility convention.                               |
| **Dominance or symmetry reduction**  | A removed candidate, or every completion of a removed branch, cannot win; identity-sensitive tie-breaking is preserved.              |
| **Certified upper-bound pruning**    | The upper bound covers the candidate or entire unexplored region, and lies below the incumbent’s established value.                  |
| **Partial-solve elimination**        | A rigorous enclosure of the final oracle result is already sufficient to decide the comparison.                                      |

These conditions are mathematical obligations, not claims that all these opportunities exist in your implementation.

In particular, **a poor singleton move does not prove that a coalition containing it is poor**. Your absence of submodularity removes precisely the sort of diminishing-returns argument that might otherwise support some simple pruning rules.

### The central certificate

For maximisation, suppose evaluation or bounding establishes

$$
F(a)\in[L_a,U_a].
$$

A candidate \(a\) can be discarded when

$$
U_a<L_{\mathrm{inc}}.
$$

The proof is direct:

$$
F(a)\le U_a<L_{\mathrm{inc}}\le F(a_{\mathrm{inc}}).
$$

For an unexplored region \(\mathcal B\), the required bound is

$$
U(\mathcal B)\ge \sup_{a\in\mathcal B}F(a).
$$

This does not require submodularity. It does require a valid and sufficiently cheap bound; a very loose bound may save nothing.

Equality needs special treatment. **Equal objective value does not mean equal selected assignment.** When \(U_a=L_{\mathrm{inc}}\), prune only when the reference tie rule also makes \(a\) unable to win.

For an adaptive reference search, there is another subtlety: even a candidate that cannot be the final winner might have a score that determines future proposals. Skipping its evaluation must preserve that control-relevant information or be accompanied by a proof that later generation is unchanged.

### A potentially useful bound for your fixed-point oracle

Here is a sufficient condition, not an assumption about your physics.

Suppose

$$
x^\star=H_a(x^\star),
$$

and \(H_a\) is a contraction with a verified factor \(q<1\) on an appropriate invariant domain. At an iterate \(x\), let

$$
r=\|x-H_a(x)\|.
$$

Then

$$
\|x-x^\star\|
\le r+q\|x-x^\star\|,
$$

so

$$
\boxed{\|x-x^\star\|\le \frac{r}{1-q}.}
$$

If \(F(a)=g_a(x^\star)\), and \(g_a\) has a known Lipschitz constant \(K_a\) over that enclosure, then

$$
F(a)\in
\left[
g_a(x)-K_a\frac{r}{1-q},
\;
g_a(x)+K_a\frac{r}{1-q}
\right],
$$

with numerical rounding error included conservatively.

This could let an early iterate eliminate a losing candidate without completing its usual solve.

However, observed convergence does not establish a contraction factor. A small residual alone is not this certificate. If the score includes hard decoding thresholds, the Lipschitz step may fail: the enclosure must explicitly account for threshold crossings and possible branches.

There is also a numerical-contract distinction. A bound on the mathematically exact \(F\) does not automatically preserve the winner chosen by a finite-tolerance reference oracle near a tie. For strict implementation equivalence, bound the reference score itself or use the unchanged reference evaluation for ambiguous cases.

### What evidence earns the word “lossless”?

I would require three things together:

**A proof under explicit assumptions.** For every skipped computation, explain why it cannot change the selected candidate or subsequent reference search.

**An implementation-level argument.** Cover cache keys, root selection, finite precision, feasibility conventions, tie-breaking and randomness—not just the ideal equations.

**Differential replay.** Run reference and accelerated implementations on identical snapshots and random inputs, comparing full selected assignments. Include ties, threshold boundaries, difficult convergence cases and adversarial examples. Keep prune certificates so an independent checker can verify why candidates were removed.

Testing can expose violations and validate the implementation. Unless it exhaustively covers the allowed input domain, zero disagreements alone is not a universal proof.

There is a fundamental limit worth stating explicitly: with a completely arbitrary black-box objective, an unevaluated candidate could have any value consistent with the observations. Without a structural bound, it cannot generally be ruled out. Your opportunity is therefore **exact reuse and model-specific certification**, not a generic lossless shortlist.

## 4. Headroom: choose a reliability target, then size the guard

**An observed maximum of 9.9 seconds is not a worst-case execution-time bound.** Without the sample count and measurement conditions, it is not even enough to identify a particular latency quantile.

For your application, separate two failure probabilities:

$$
\epsilon_{\mathrm{return}}
=
P(\text{no valid assignment published by 10 s}),
$$

$$
\epsilon_{\mathrm{selection}}
=
P(\text{reference selection unavailable before the internal cutoff}).
$$

An independent fallback path can make the first very small while leaving the second large. That would improve operational behaviour without rescuing the experiment.

### Headroom should come from the output path and the tolerated miss rate

Let \(B\) be the acceptance cutoff measured from epoch release, and let \(H\) include the remaining scheduling delay and publication work. The return requirement is

$$
P(B+H>10)\le\epsilon_{\mathrm{return}}.
$$

A statistical guard would be based on an upper confidence bound for the relevant tail quantile of \(H\), plus an explicitly justified allowance for deployment variation:

$$
B=10-G.
$$

A genuine hard guarantee instead needs a defensible upper bound on \(H\) and a schedulable execution environment.

Separately, the accelerated procedure needs to satisfy

$$
P(T_{\mathrm{certificate}}>B)
\le\epsilon_{\mathrm{selection}}.
$$

**Moving the cutoff earlier without accelerating certification increases headroom by increasing fallbacks.** It is not a solution to your measurement problem.

Do not add the same percentile of each stage and call the result that percentile of total latency. Measure the joint end-to-end distribution, or allocate failure probabilities across stages and use a conservative union-bound argument.

### Decide what fallback rate the experiment can tolerate

At one decision every 30 seconds, there are 2,880 decisions per day. By direct calculation, a per-decision fallback probability of 1% corresponds to 28.8 expected fallback epochs per day; 0.1% corresponds to 2.88; 0.01% corresponds to 0.288.

Those are illustrations, not recommended targets. Your acceptable rate should follow from the experiment’s required treatment contrast and statistical power, including whether misses cluster on particular anchors.

For a fixed, preselected cutoff and independent representative trials, zero misses in \(n\) trials gives the one-sided 95% binomial upper bound

$$
p_{\mathrm{miss}}\le 1-0.05^{1/n}\approx\frac{3}{n}.
$$

Thus roughly 3,000 zero-miss trials are needed to support \(p_{\mathrm{miss}}\lesssim10^{-3}\), and roughly 30,000 for \(10^{-4}\), under those assumptions. This follows from exact binomial confidence-bound reasoning; NIST discusses the underlying construction. ([NIST 技術系列出版物][7])

Repeated, correlated evaluations of a small anchor set are not automatically that many independent representative trials. Also, use held-out measurements after choosing the guard rather than treating the data used to tune it as untouched validation.

### Heavy tails need workload coverage, not “mean plus three sigma”

I would characterise the difficult regimes explicitly: repeated runs of the same hard anchor to measure system variation, different hard anchors to measure workload variation, cold and warm execution, and the actual resource contention expected during the experiment.

Extreme-value methods can help analyse tails, but they do not remove the need for representative samples and justified distributional assumptions. Research on probabilistic worst-case execution time specifically identifies representativeness and sensitivity to tail-fitting choices as central difficulties. ([白玫瑰研究在線][8])

Preserve timeout observations. A latency distribution containing only successful decisions is censored in exactly the region you care about. Separate diagnostic runs without the production cutoff can reveal whether certification would have finished at 10.1 seconds or 40 seconds.

### Measure experimental harm directly

Let \(M\) indicate fallback, and let \(\Delta\) be the completed reference decision’s gain over keeping the previous assignment, for the same snapshot. The realised gain attributable to issuing that decision is

$$
G=(1-M)\Delta.
$$

Consequently,

$$
E[G]=E[(1-M)\Delta],
$$

which is not generally \((1-P(M))E[\Delta]\). Difficult or high-gain anchors may also be slow.

Report per-arm fallback rates, consecutive fallback runs and unconditional outcomes, with successful-only outcomes as diagnostics. Otherwise, a faster arm or an arm that times out on different anchors can change the comparison independently of decision quality.

**The supplied 5.7–9.9-second range cannot justify any particular safe guard.** A numerical recommendation such as “reserve 20%” would be a heuristic, not a conclusion from your measurements.

## 5. What real wireless and satellite systems establish—and what they do not

The public evidence supports a distinction between **control cadence**, **optimiser runtime allowance** and **fallback behaviour**. They should not be substituted for one another.

| Evidence                                                           | Documented timescale or behaviour                                                                                                                                                  | What it does not establish                                                                                                                                                                         |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **O-RAN control architecture**                                     | Near-real-time control is commonly described as 10 ms–1 s; non-real-time control operates on timescales of 1 s or more. Your 30-second loop fits the slower supervisory timescale. | A measured solver runtime or hard deadline for your optimisation problem. ([1FINITY][9])                                                                                                           |
| **Measurements of deployed Starlink links, published at WWW 2024** | Controlled measurements identified globally synchronised **15-second link-reconfiguration intervals**.                                                                             | How long the internal optimiser ran, how far ahead it planned, or what happened on an optimiser timeout. This is a dated observation, not proof that the cadence is unchanged today. ([arXiv][10]) |
| **Cisco commercial wireless-controller DCA documentation**         | Dynamic channel assignment runs every **10 minutes by default** in the documented steady-state configuration.                                                                      | Ten minutes of solver computation. It illustrates that supervisory resource-control cadence can be much slower than packet-level operation. ([Cisco][11])                                          |
| **O-RAN use-case specification, April 2025**                       | A beam-based mobility-optimisation use case explicitly provides for restoring previous/default configurations when optimisation performance is unsatisfactory.                     | A measured deployment’s timeout policy; the stated trigger is unsatisfactory performance, not specifically solver noncompletion.                                                                   |

Therefore, I would **not** justify your 10-second budget by saying that deployed satellite systems reconfigure every 15 seconds. A network could compute ahead, pipeline plans, use a much cheaper decision rule, or allocate only a fraction of the reconfiguration interval to optimisation. The cited measurement does not distinguish those possibilities.

Your existing “keep the previous assignment” policy is consistent with the previous/default-configuration fallback pattern in the O-RAN specification, but that does not make a high fallback rate acceptable for your experiment.

At the optimiser interface, the policy choices remain distinct: use a completed and eligible recommendation, use an uncertified feasible incumbent when approximation is permitted, or retain a validated previous/default configuration. Under your stated restriction, the middle choice is unavailable unless you explicitly change the experimental method.

## Recommendation for this experiment

**Keep the candidate-selection contract fixed. Profile time to certification at the difficult anchors, then remove redundant exact evaluations and repeated invariant work before changing the search.** Introduce stronger pruning only where you can produce a valid bound, including the numerical and tie-breaking details.

In parallel with those implementation changes, make the supervisor’s return independent of solver completion. This prevents an overrun from corrupting or withholding the committed assignment, but should not be counted as reducing experimental fallbacks unless the original selection is actually available earlier.

The acceptance result you need is not merely “mean latency improved” or “the function always returns.” It is:

> **The accelerated procedure preserves the reference-selected assignment, and its time-to-certificate distribution meets a predeclared fallback-rate target before a separately validated publication cutoff.**

The public sources establish relevant control cadences and rollback mechanisms, but do **not** disclose a comparable deployed system’s internal 10-second optimiser bound or timeout rate. They support the architecture above; they cannot supply the missing headroom number for your implementation.
